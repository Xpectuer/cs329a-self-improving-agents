# 可验证领域（Verifiable Domains）

> Source(s): raw/ch-06-自动化验证的必要性与可验证领域, raw/ch-02-RLEF, raw/ch-04-论文三：DAPO（长链推理的强化学习稳定化）, raw/ch-05-总结：闭环自我改进与可验证领域

在自动化验证的背景下，我们需要从大量生成样本中判断哪些是正确的，以及如何选择它们。某些领域比其他领域更容易验证，这为构建可靠的生成系统提供了天然优势。验证机制的关键在于：它必须**比生成任务本身更简单**，从而能够在无需人工逐项检查的前提下，大规模筛选正确样本。

## 数学：形式化证明

对于某些类型的数学问题，可以使用形式化证明。给定一个证明或策略，可以借助形式化证明软件工具逐步验证每一步是否正确。这类工具提供机械化的严谨校验，使得数学推理的验证成为可能。

## 编程：单元测试

我们可以为代码编写单元测试。在某些情况下，编写单元测试比编写整个解决问题的程序要简单得多。单元测试可以由人类编写，然后作为生成代码的验证器。例如，当我们让模型生成程序时，可以用预先编写的测试用例来判断输出是否符合预期。

### 执行反馈：从单元测试到代码生成中的 RLEF

“单元测试作为自动验证器”的思想在代码生成场景下有一个更具体的实现——**执行反馈（Execution Feedback）**。RLEF 方法（grounding code LLMs in execution feedback）聚焦于如何在代码生成过程中利用运行代码或运行测试所获得的反馈信号。通过实际执行生成的代码，我们可以获得运行时正确性信号，这些信号不仅用于筛选结果，还可以作为引导信号，帮助模型在生成过程中持续修正和改进。这本质上就是把“运行测试”这一验证动作，从简单的判别器升级为引导代码语言模型学习的反馈源。

## 语言间转换：输出等价性

一个更有趣的方向是“AI 作为编译器”，例如用大型语言模型将 PyTorch 源码生成更底层的 CUDA 代码。之所以可验证，是因为对于任意给定输入，我们都可以比较 CUDA 代码和源 PyTorch 代码的输出是否一致。如果输出匹配，就可以断定生成的 CUDA 代码是正确的，无需额外的人工检查。

### AI-as-a-Compiler 与 KernelBench

CUDA 是一种面向 GPU 的低级语言，用于编写更贴近硬件、更注重性能优化的代码。AI-as-a-Compiler 指的就是使用 LLM 自动执行这种高级别到低级别的转换。这类任务天然具备“完美验证器”：只要所有输入下生成代码与源程序输出一致，就能确认功能等价，而无需逐行审查代码。

这里有一个名为 **KernelBench** 的基准数据集，用于评估 CUDA 代码生成。研究观察到，随着从模型中采样的样本数量增加，CUDA 代码生成的覆盖率呈线性提升。在这种场景下，每个采样都可以通过默认的完美验证器自动判断正确性，从而支撑这一规律。

### 更广泛的适用性

AI-as-a-Compiler 的思想可以扩展到任何两种语言之间的翻译任务。例如：

- 将 Python 或 C++ 代码移植到 Java，或反向移植。
- 任何两种语言之间的翻译（如 Python 到 C++、C++ 到 Java）都具有这种特性：可以通过比较输入输出等价性来轻松验证转换的正确性。

只要能够测量两种代码在任意输入下的行为等价性，验证就会变得容易得多。

## 验证器与扩展规律

以 KernelBench 为例，在具备自动化验证器的领域，推理期扩展的收益可以稳定、可靠地被度量。随着采样数量增加，覆盖率呈线性提升，这表明“生成-验证”范式可以支撑大规模采样，并直接将采样规模转化为更高的可靠性与覆盖率。

这种扩展规律不仅存在于推理期。在可验证领域中，类似的“生成-验证”回路还可以用于训练阶段，即**训练时扩展（train-time scaling）**。

## 可验证性与训练时扩展

训练时扩展的核心思想是：让模型从自身输出中学习——通过自动化验证器巧妙筛选正确样本，再将这些样本用于强化学习或进一步微调，从而提升模型能力。这构成一个闭环：模型生成输出 → 验证筛选 → 训练改进 → 再次生成。

以数学推理基准 AIME 为例，GPT-3.5（约175B参数）的准确率接近5%，而7B参数的 DeepSeekMath 通过训练时扩展达到51.7%甚至60%的准确率；DAPO（一种面向长链推理的强化学习稳定化算法）应用于 Qwen-32B 后同样能达到50%。这说明训练时投入的计算可以在一定程度上替代模型参数的增长。o1 的研究也表明，在 AIME 上同时增加训练时计算和测试时计算都能提升 pass@1 准确率，支持了这一“生成-筛选-再训练”的回路。

为什么这个闭环在数学领域特别有效？因为数学是可验证的（参见上文“形式化证明”），我们能够精确判断输出是否正确，从而获得高质量的训练信号。这和执行反馈（RLEF）的思路一脉相承：验证机制不仅用于筛选，还作为学习信号指导模型修正。

### DAPO：稳定化 RL 的关键细节

值得注意的是，训练时扩展（尤其是强化学习）对实现细节高度敏感。当算法规模化时，一些看似微小的修正可能至关重要，这也是 DAPO 等稳定化方法存在的意义。DAPO 的研究者发现，随着训练推进，模型生成的推理链会越来越长，而许多细节问题会干扰优化：

- **样本级损失的缺陷**：在 GRPO 等算法中，如果对每个问题-答案对计算整个序列的损失，长而无用的“垃圾答案”与短而正确的答案会被赋予相同的权重，这会引入大量噪声。DAPO 提出改用 **token 级损失**，并结合长度整形（length penalty），使每个 token 的贡献得到更合理的分配。
- **熵与响应长度控制**：如果没有 token 级损失，序列的熵会逐渐增长，响应长度也会失控。通过施加适当的惩罚，可以更好地塑造这两个指标，让训练更稳定。
- **软超长惩罚（soft overlong punishment）**：当模型遇到难题时，推理链往往被截断，产生大量噪声。DAPO 对超长 token 施加逐渐增强的惩罚，避免截断造成的训练不稳定。

这些修正的效果在 AIME 基准上非常明显。从 GRPO 出发，逐步叠加各项技术后，Qwen-32B 的分数变化如下：

| 技术 | AIME 分数 |
|------|-----------|
| GRPO 基线 | 30 |
| + 超长过滤（overlong filtering） | 36 |
| + 非对称裁剪（asymmetric clipping） | 38 |
| + 软超长惩罚 | 41 |
| + token 级损失 | 42 |
| + 动态采样（dynamic sampling） | 50 |

动态采样通过更均匀地在批次内分配奖励，改善了信号传播。最终 50 分甚至超过了 DeepSeek-R1 蒸馏到 Qwen-32B 的水平，证明在可验证领域中，即使基座模型不变，仅靠 RL 训练也能实现 strong hill climb。

### RL 学习中的实践原则

DAPO 的经验总结出几条 RL 训练的重要原则：

- 损失函数本身并不是足够好的代理指标。训练时需要同时关注**响应长度**和**熵**：熵不能太高（会导致随机性过大），也不能太低（会导致探索不足）。
- **全精度为 1 的样本比例**（即完全正确的响应占比）决定了需要多少采样量。
- 常见挑战包括：响应长度爆炸（需要控制损失）、熵失控（需要调节生成参数）、以及奖励模型饱和（如果多步后无改进，说明奖励信号已经无法区分优劣）。

### RL 与 SFT 的对比

在可验证领域，RL 的确提供了更强的**爬山（hill climb）能力**：只要奖励信号可靠，模型可以用更少的样本在已有能力上不断攀升。但 RL 的训练稳定性需要大量调优。相比之下，监督微调（SFT）在拥有大量高质量数据时往往更快，但通常不会带来根本性的推理能力提升。

对于不同资源条件，可以这样选择：

- **少量样本（约 100 个推理示例）**：如果没有 RL 基础设施，**STaR** 是让模型开始推理的简单方法。简单任务如 GSM8K 会得到合理提升，但不会突破模型原有的能力边界。
- **有限 GPU + 较好的基座模型**：**DeepSeekMath 的 GRPO** 是一个稳健的选择，只要用良好的指令数据预训练基座模型，即可在标准数学推理任务上生效。
- **长链推理 + 竞赛级难题（AIME/IMO）**：需要控制上述所有变量，采用 DAPO 这类稳定化 RL 算法和基础设施，才能获得最佳效果。

总的来说，这些技术普遍会提升 **pass@k**、**答案格式合规性** 和 **多步推理的连贯性**，但还无法让模型学会根本性的新能力或大幅度跨领域泛化——这仍是当前研究的开放问题。

## 核心要点

- 可验证领域的关键在于拥有一个**比生成任务更简单的验证机制**。
- 形式化证明、单元测试、输入输出等价性比较都是典型的
