# AlphaCode

> Source(s): raw/ch-01-课程引言：通过搜索实现自我改进, raw/ch-02-AlphaCode 问题背景与定义, raw/ch-03-AlphaCode 流水线：预训练与微调, raw/ch-04-AlphaCode 大规模采样与候选生成, raw/ch-06-课堂讨论与问答

AlphaCode 和 AlphaCode 2 是代码生成领域搜索范式的代表系统。它们的核心思想是：在推理时通过大规模采样生成大量候选解，然后利用搜索、筛选、聚类等手段从中精选出少量高质量的提交答案。这种模式与受限提交指标 10@k 紧密相关。与 pass@k（允许模型的所有 k 个生成样本都参与评测）不同，10@k 意味着即使模型生成了 k 个候选解（如 100 万个），最终也只能提交 10 个用于隐藏测试。因此，10@k 不仅衡量采样过程对解的“覆盖”程度，也衡量模型从海量候选中筛选出最优解集的“策展”能力。

## 问题背景与目标

AlphaCode 要解决的问题比简单的代码补全 agent 更复杂。常见的 coding agent 往往只做自动补全：你写一行代码，它帮你补完这一行。而 AlphaCode 面向的是竞赛编程问题：给定问题描述，再给定一些输入和输出样例。这些输入/输出对构成了问题中的“契约”——如果给出一组输入，就应当得到对应的一组输出。真正要解决的，是如何端到端地解决这类竞赛编程问题。

单行代码补全之所以容易，是因为开发者可以逐行与模型交互，成功率也更高，例如 Copilot 等工具的效果。但当模型需要生成整段代码、真正从头到尾解决问题时，难度显著增加。竞赛编程问题的描述更长、解法代码也更长，模型必须先理解题目意图，再确定正确的解题思路，而不能像 HumanEval 中那样只补全一个函数或按明确指令执行。

## 早期成就

AlphaCode 已经是近四年前的论文，但它当时的成就仍值得回顾：在 10 场竞赛中，AlphaCode 的排名进入参赛者的前 54%。这是 AI 首次被证明能够超越狭窄任务，端到端地解决真实问题。相比 HumanEval 这类只需完成小函数、不需要理解问题背景的任务，竞赛编程问题要求模型同时完成问题理解与方案设计。

## 流水线

AlphaCode 的完整流程分为几个阶段。

### 1. 训练模型

在大型预训练模型普及之前，AlphaCode 需要预训练自己的模型；这一阶段的模型后来可以被大型语言模型替代。预训练与微调使用的数据来自 GitHub 和 code contests。code contests 包含大量来自竞赛编程的问题与解答。

预训练阶段，AlphaCode 在约 700GB 的 GitHub 代码上进行训练。AlphaCode 最初采用 encoder-decoder 架构，使用 masked language model loss；AlphaCode 2 则尝试了 decoder-only 模型，改用 next token prediction。这一架构演进反映了从编码器理解到纯解码器生成的转变。

微调阶段使用了一些技巧：
- **正则化（GOLD）**：在 next token prediction loss 中引入 token 似然加权——对高似然 token 赋予更高权重、对低似然 token 赋予更低权重。这相当于在损失计算中加入一个权重机制，考虑 token 自身出现的可能性，从而将概率分配向更有意义的模式倾斜，提升生成精度。
- **value conditioning and prediction（值条件化与预测）**：这是微调中的另一项技巧，本材料仅提及名称，未展开具体细节。

### 2. 大规模采样

获得训练好的模型后，AlphaCode 进入大规模采样阶段。对每道竞赛题，AlphaCode 会生成约 100 万个候选解，其中约一半用 Python、一半用 C++。为了让这些候选解足够多样，AlphaCode 在 prompt 中随机化题目标签（problem tags）和题目难度评级（ratings），并使用较高的采样温度。这些策略共同保证生成解在算法思路、实现方式和边界行为上具有显著差异，为后续筛选提供足够大的搜索空间。

课程中特别指出，采样规模与模型规模之间存在权衡：模型越小，为达到相同的 pass@k 或 10@k 往往需要生成更多的样本；而更大的模型（如 41B 相比 9B）在相同采样规模下通常表现得更好。这就是推理时扩展（inference scaling）中常见的行为趋势。

### 3. 筛选与聚类

生成百万级候选解后，AlphaCode 并不会把所有候选解都拿去最终评测，而是先做筛选和聚类。

- **过滤样例测试**：首先过滤掉未通过题目描述中给定样例测试的候选解。这是整个策展流程的第一道关卡——在大规模采样之后，只有通过这些自带测试用例的候选解才有资格进入后续的聚类与选择阶段。
- **语义聚类**：然后对通过样例测试的解进行聚类，目标是得到“语法上不同、语义上等价”的候选组。由于同一道题可以有多种写法，聚类旨在把实现不同但行为一致的解归入同一簇，避免重复提交同质解。

为了实现这种语义聚类，AlphaCode 额外训练了一个测试输入生成模型。该模型学会根据问题描述预测可能的测试输入，并能为新的未见过问题生成新测试输入。AlphaCode 借助这些新生成的测试输入运行候选解，通过比较它们的输出来判断行为是否等价，从而把语义等价的解聚到一起。语义等价只是实现这一目标的一种方式，实际中还会使用其他技巧来构造与选择测试输入。

这一步体现了 AlphaCode 搜索模式的关键思想：模型已经将解蕴含在其搜索空间中，关键问题是如何从模型输出的搜索空间中“策展”出最终答案；而不是把全部候选解简单执行一遍。

**模型规模、聚类与 10@k 的效果**：课堂讨论中展示了 AlphaCode 在验证集与测试集上的 10@k 结果，对比了不同模型规模和是否使用聚类的影响。在验证集上，随着生成样本数从 1k 增加到 100 万（记为 10@1k、10@10k、10@100k、10@1M），10@k 持续提升；测试集也呈现类似趋势。同时，更大的模型（41B）一致优于较小的模型（9B）。在 41B 模型上加入聚类后，性能进一步提升，并且这一优势在各类上下文（context）和样本规模下都保持稳定。聚类之所以有效，是因为在只能提交 10 个解的限制下，提交语义多样、覆盖不同解法的候选组能比提交重复的同质解带来更高的成功率。

### 4. 执行与评估

筛选与聚类结束后，对得到的代表性候选解进行编译、执行与评测，最终产出可提交的高质量答案。

课程中强调，AlphaCode/AlphaCode 2 的搜索模式会在作业二的 HumanEval 任务中得到应用，用于相对简单的问题；而更复杂的 agent search（如深度研究风格）则在作业三中出现。整个方法的核心认知是：模型已经将解蕴含在其搜索空间中，关键问题是如何从模型输出的搜索空间中“策展”出最终答案。

课堂讨论还回答了为什么不同上下文（context）下性能表现差异明显的问题。可能的原因主要有两点：一是不同竞赛问题的输入分布本身存在难度差异，模型在某些问题上可能更“偏离分布”或更难理解；二是在筛选阶段，某些问题中“几乎正确”的候选解可能无法被正确识别出来，导致选择阶段成为瓶颈。因此，采样阶段的覆盖范围和筛选阶段的精确性共同决定了最终 10@k 的表现。

这种通过搜索实现自我改进的思路，连接了采样、生成、验证和选择等多个环节，是推理时扩展（inference scaling）的重要实践。
