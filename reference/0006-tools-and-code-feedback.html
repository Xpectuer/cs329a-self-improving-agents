工具与代码反馈速查卡

第 5 课配套参考 · 「执行反馈」是把验证从判词变动作的关键

一句话：模型不靠「想」改答案，靠「做」拿反馈——执行代码、跑测试、调用工具，用真实结果修正自己。

1. 工具调用：从生成器到智能体

LLM 只生成文本；带工具的 agent 能调用代码解释器、搜索引擎、API、模拟器，执行动作、读取环境结果、多步迭代。工具是「智能体」与「生成模型」之间的枢纽；符号技术也属于工具使用（且是合成数据来源之一）。

2. 反馈的类型与强度

类型机制例子强度
静态答案匹配生成后单次比对数学答案、选择题判别式，无法指导中间步
执行反馈运行代码/测试，看真实结果pytest、编译器、解释器验证行为而非表面
环境交互工具调用返回观测网页、search API、模拟器动态、可多步

3. 可验证领域 = 执行反馈的天然土壤

领域验证器备注
数学形式化证明（Lean 等）机械严谨，逐步校验
编程单元测试写测试比写程序简单；RLEF 用执行反馈做 RL 信号
语言转换输入/输出等价性AI-as-a-Compiler（PyTorch→CUDA）；KernelBench 上覆盖率随采样线性提升

验证器必须比生成任务更简单，才能大规模自动化——否则只是把难题换了个地方。

4. 代码反馈的两种用法

  • 筛选：跑测试 → 保留通过的候选（第 3 课 AlphaCode 流）
  • 学习信号：执行结果作为奖励喂给 RL（RLEF）——把验证动作从「判别器」升级为「引导信号」

5. Agent Search：搜索空间从「代码」到「轨迹」

代码模型搜索 = 大量采样 + 筛选（AlphaCode/AlphaCode 2）；智能体搜索 = 在深度研究式长任务中，于动作/轨迹空间搜索，算法示例 LATS。

6. LATS 六阶段（MCTS × LLM，测试时搜索）

  1. 选择：UCT 平衡探索/利用，选扩展节点
  2. 扩展：采样多个候选行动，并行执行，观测追加上下文
  3. 评估：$s = s_{LM} + \lambda\, s_{SC}$（LLM-as-Judge 打分 + 自洽性频率分数）
  4. 模拟：从最高分状态贪心推进至终点/预算
  5. 反向传播：结果回传更新路径分数
  6. 反思：对成功/失败轨迹生成解释，回喂后续搜索

HotPotQA / WebShop 无需微调即接近人类专家；提醒：隐含假设行动可逆，交易/支付等不可逆场景慎用；成本未系统分析。

6.1 LATS 的地基假设：环境可回放（共享资源问题）

树搜索从父状态分岔 = 执行 $a_1$ → 回到父状态 → 再执行 $a_2$……所以 LATS 真正依赖的不是「行动可逆」，而是环境可回放（可重置 / 无副作用）。模拟器、检索、沙箱都满足；真实物理资源（如互斥设备：一次只能操作一台）不满足——原版 LATS 未处理这类冲突，评测环境从不会遇到。

适用性三问回答「否」的后果
① 环境可重置？（可回到任意历史状态重放）树分岔在物理上不可能 → LATS 直接失效
② 动作可逆？（错了能撤销）探索被真实后果惩罚，只能一次性下注
③ 副作用可观察？（冲突/占用能被环境反馈表达）无信号可学——学了也白学

适配方向（工程思路，超出论文本身）：

  • 环境可模拟（digital twin / 沙箱）→ 把「设备占用表」建模进状态，冲突动作返回负反馈——冲突观察也是执行反馈（见 §2），MCTS 自然学会避开
  • 只读可搜索 + 物理不可逆 → 分层执行：树只在决策/只读层跑，物理动作放搜索末端一次性执行
  • 完全不可模拟/不可逆 → 换世界模型规划（第 6 课的主题域）

判别口诀：可回放 → 直接用；可模拟 → 建模进状态；只读层 → 分层执行；都不行 → 世界模型。

7. 与闭环四步的对接

「生成 → 验证（执行反馈） → 学习（RLEF/RL） → 搜索（LATS）」——工具执行既是验证器，又是学习信号源，还是搜索的探针。这正是「通过搜索实现自我改进」的第 2 讲主线在工具层的落地。
